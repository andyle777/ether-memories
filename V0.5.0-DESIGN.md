# Ether Memories v0.5.0 — Deterministic Retrieval & Memory Intelligence

This document freezes the v0.5.0 preparation baseline. It describes the
release boundary before implementation of the new retrieval engine.

## Release intent

v0.5.0 will improve deterministic retrieval and memory intelligence while
remaining a small, local-first, provider-neutral memory library. Notes, Diary,
Mind Graph, snapshot persistence, MemoryContext, and Portable Records remain
the public foundation. Condensation remains a processing layer rather than a
fourth foundation.

The library version will become `0.5.0` during implementation. The persisted
schema contracts do not change:

- `STORE_SCHEMA_VERSION = "ether.memory_store.v0.3"`
- `MEMORY_CONTEXT_SCHEMA_VERSION = "ether.memory_context.v1"`
- `PORTABLE_RECORD_SCHEMA_VERSION = "ether.portable_record.v1"`

No release tag or `main` branch is changed by this preparation work.

## Current v0.4.0 compatibility boundary

The v0.4 implementation currently provides:

- `MemoryNotes` with clone-on-read Notes, metadata/provenance, lifecycle
  status, expiry, pinned editing, and candidate promotion.
- `DiarySystem` with CRUD, tags, metadata, and chronological reads.
- `MindGraphManager` with directed, single-edge endpoint relationships,
  stable edge IDs, structural neighborhoods, and bounded recall traversal.
- `MemoryRetriever` with deterministic lexical matching, evidence-only
  `matchedBy`, explicit-ID candidates, candidate/archive/expiry/pinned/
  tag/category filters, optional graph-assisted recall with path evidence,
  canonical Unicode tokenization, match classes, `asOf`, and a derived
  revision-aware lexical index.
- `MemoryContextBuilder` with explicit IDs, Note and Diary retrieval,
  graph slices, citations, budgets, deterministic retrieval traces, and
  character truncation accounting.
- `CondensationEngine` and `FoundationLinker` lifecycle integration.
- Transactional snapshot import/export, identity restoration, user-ID
  protection, injectable `StoragePort`, and crash-safer filesystem storage.
- Portable Note/Diary records through `toPortableRecords()`.
- Transactional Portable Record v1 preflight/import that preserves only
  represented Note/Diary fields and never imports identity or graph state.

The existing v0.4 public API remains the compatibility baseline. v0.5
implementation work must preserve existing calls and result shapes unless a
change is explicitly required by the frozen retrieval specification.

## Canonical persistence versus interchange

### Snapshot persistence

`ether.memory_store.v0.3` is canonical, lossless persistence for the complete
library state:

- identity and preferences;
- Memory Notes, including metadata, provenance, lifecycle, and dates;
- Diary entries;
- the complete Mind Graph, including stable edge IDs and edge data.

Snapshot import/export is not interchangeable with Portable Records. Snapshot
validation remains transactional: rejected input must not partially mutate
Notes, Diary, graph, identity, or preferences.

### Portable Record v1

`ether.portable_record.v1` is Note/Diary interchange only. A Portable Record
does not carry the complete `MemoryNote`, identity, full Diary system, or Mind
Graph. It is derived from a bounded `MemoryContext` and is not a portable
snapshot format.

## Compatibility fixtures

The following fixtures are captured from the current v0.4.0 implementation and
must remain readable and behaviorally stable during v0.5 work:

- [`tests/fixtures/store-v0.3.json`](./tests/fixtures/store-v0.3.json) —
  canonical `ether.memory_store.v0.3` JSON with identity, five Notes, one
  Diary entry, graph nodes, and a stable graph edge.
- [`tests/fixtures/portable-record-v1.json`](./tests/fixtures/portable-record-v1.json) —
  actual `toPortableRecords()` output using
  `ether.portable_record.v1`; it contains Note/Diary interchange records only.
- [`tests/fixtures/retrieval-golden-v1.json`](./tests/fixtures/retrieval-golden-v1.json) —
  fixed-corpus golden outputs for default retrieval, all candidate/archive/
  expiry filters, graph recall, graph evidence, context selection/citations,
  truncation, and Portable Record IDs/schema.

The corpus uses fixed 2020 timestamps so the current recency term is zero and
the recorded scores do not depend on wall-clock time. Query ordering, scores,
`matchedBy`, graph path/edge evidence, candidate filtering, archived
filtering, and expiry filtering are intentionally explicit in the golden file.
When a future implementation changes a golden result, the change must be
treated as a compatibility decision, not an incidental test update.

The original v0.4 golden values used accumulated lexical/filter modifiers and
did not expose match classes. The v0.5 golden file intentionally records the
new class-gated scores and `matchClass` values. Canonical tokenization and
code-unit ordering are also intentional v0.5 semantics; the canonical store
fixture and Portable Record shape remain compatible.

## Frozen retrieval behavior

The v0.5 retrieval implementation must remain:

- deterministic for the same store, query, options, and frozen time;
- provider-neutral and based on local library data;
- explicit about evidence in `matchedBy`;
- explicit about graph path/depth evidence;
- consistent with candidate, archived, expiry, pinned, tag, and category
  filtering;
- bounded when projected through `MemoryContext`;
- compatible with the existing default graph-off behavior.

Scores, ordering, and evidence in the fixture are the current released
behavioral baseline. No vector, embedding, semantic-provider, or network
operation is implied by “memory intelligence.”

The lexical index is derived runtime state. Notes and Diary remain canonical
truth, and the index is rebuilt synchronously whenever the corresponding
manager revision changes. Revisions are runtime-only and are not persisted.
The first query after a large mutation or snapshot import may therefore incur
a full index rebuild. `rebuildIndex()` is available as an optional warm-up;
correctness does not depend on calling it.

## Explicit v0.5 deferrals

The following are outside v0.5.0:

- SQLite;
- IndexedDB or browser persistence;
- vectors or embeddings;
- semantic model providers;
- graph visualization;
- automatic memory decay;
- authentication or multi-tenancy;
- distributed synchronization;
- Portable graph transport;
- a generalized transaction language.

The project also remains outside the scope of autonomous memory systems,
personality systems, agent orchestration, private framework integrations,
provider-specific dependencies, and unrelated experimental architecture.

## Implementation boundary

This preparation milestone adds only this frozen design record and captured
compatibility fixtures. It does not implement the v0.5 retrieval engine,
change schemas, alter persistence semantics, or redesign the architecture.
